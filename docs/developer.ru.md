# Руководство Для Разработчиков

English version: [developer.md](./developer.md)

Этот документ описывает, как устроен `awesomer` на уровне кода и как данные проходят через приложение. Он предназначен для разработчиков, которым нужно менять поведение, добавлять возможности или отлаживать взаимодействие между TUI, демоном и Linux-специфичными backend-ами.

## Цели Архитектуры

Кодовая база организована вокруг нескольких практических целей:

- изолировать чтение информации о процессах Linux от UI-кода;
- изолировать детали backend-а ограничения ресурсов от логики демона и сервиса;
- держать TUI тонким и событийным;
- переиспользовать snapshot процессов между TUI и демоном, чтобы не делать лишние обходы `/proc`;
- делать side effects подменяемыми в тестах через function variables и небольшие интерфейсы.

## Архитектура Верхнего Уровня

Во время работы проект разделён на две точки входа и набор общих пакетов:

1. `cmd/awesomerctl`
   Точка входа клиента `awesomerctl`: загрузка конфига, настройка логгеров, создание collector-а и запуск TUI.
2. `cmd/awesomerd`
   Точка входа демона `awesomerd`: загрузка конфига, запуск демона, запуск IPC socket и graceful shutdown по сигналам.
3. `internal/collector`
   Общий краткоживущий кэш snapshot-ов процессов и деревьев процессов.
4. `internal/service` и `internal/service/tui`
   Пользовательский список процессов, сортировка, локальные действия над процессами и обработка событий Bubble Tea.
5. `internal/daemon`
   Фоновый цикл контроля ресурсов плюс Unix-socket IPC, через который клиент управляет демоном.

Поддерживающие пакеты:

- `internal/config`
  YAML-конфиг и значения по умолчанию.
- `internal/daemon/info`
  Абстракция jail-state, которая используется и in-process, и через IPC-клиент.
- `pkg/parser`
  Низкоуровневое чтение процессов через `gopsutil`.
- `pkg/mutation`
  Низкоуровневые helper-ы для CPU affinity и rlimit.
- `pkg/cgroups`
  Выбор backend-а между `systemd` и прямым `cgroup v2`.
- `pkg/logger`
  Создание логгеров приложения и демона.

## Ответственность Пакетов

### `cmd/awesomerctl`

`main.go` намеренно содержит только orchestration-логику:

- убедиться, что конфиг существует в Linux search path;
- загрузить конфиг;
- создать общий process collector;
- подключиться к daemon socket, если он существует;
- создать логгеры;
- запустить TUI.

Путь старта построен вокруг подменяемых function variables, например `loadConfigFn`, `newRemoteStateFn` и `runTUIFn`. За счёт этого client entrypoint можно тестировать без запуска реального демона и Bubble Tea программы.

### `cmd/awesomerd`

`main.go` — отдельный launcher для демона:

- убедиться, что root-конфиг существует;
- отказаться от запуска без root;
- загрузить конфиг и потребовать `daemon.run=true`;
- создать `info.API`, collector, daemon logger и daemon instance;
- поднять IPC socket `/run/awesomer.sock`;
- крутить enforcement loop до `SIGINT` или `SIGTERM`.

### `internal/config`

Этот пакет владеет схемой конфигурации и default-значениями.

Что важно:

- `ReadConfig()` читает YAML по вычисленному пути конфига и накладывает его поверх defaults;
- `ResolveConfigPath()` зависит от привилегий: non-root использует `~/.config/awesomer/config.yaml`, root использует `/etc/awesomer/config.yaml`;
- `DefaultConfig()` — единственное место, где задаются значения по умолчанию;
- daemon- и UI-конфиг вложены, а не разнесены по плоскому пространству имён.

Если добавляешь новую опцию, нужно обновить:

- struct tags в config-типах;
- default constructor;
- `internal/config/config.yaml.example`;
- пользовательскую документацию.

### `internal/collector`

Collector — это общий источник snapshot-ов процессов для демона и сервисного слоя TUI.

Он предоставляет:

- `Processes()`
  Возвращает краткоживущий кэшированный срез `parser.Info`.
- `ProcessTree(pid)`
  Строит и кэширует карту `PPID -> children` и post-order обход для заданного PID.

Важное поведение:

- lifetime кэша намеренно короткий;
- наружу данные возвращаются в виде копий;
- при записи нового process snapshot кэш деревьев инвалидируется.

Это основное место для дальнейшей оптимизации глобального polling-а процессов без протаскивания кэш-логики в UI или демон.

### `pkg/parser`

Parser отвечает за дорогой низкоуровневый сбор информации о процессах.

У него есть два класса API:

- дешёвые или относительно дешёвые snapshot API:
  - `AllProcesses()`
  - `ProcessTree()`
  - `ProcessInfo()`
- дорогой API подробностей:
  - `HardObjectParse()`

`AllProcesses()` вызывает `ProcessInfo()` через bounded worker pool. Parser ничего не знает о TUI-таблице, лимитах демона и состоянии process jail.

### `internal/service`

Пакет сервиса преобразует сырые process snapshot-ы в данные, которые может отрисовать TUI или над которыми можно выполнить действие.

Основные обязанности:

- сортировка списка процессов;
- форматирование строк таблицы;
- запоминание, изменилось ли визуальное состояние таблицы с прошлого обновления;
- действия над процессами: stop/resume/kill и т.д.;
- ручной toggle process jail;
- построение простого ASCII-дерева процессов для панели деталей.

`GetProcesses()` специально делает больше, чем просто fetch:

- читает текущий shared snapshot из collector-а;
- сортирует его в соответствии с выбранным режимом;
- вычисляет daemon marker `*`;
- сравнивает нормализованное состояние строк с предыдущим render state;
- возвращает `changed=false`, если для пользователя таблица осталась такой же.

За счёт этого TUI может не вызывать `SetRows()` без реального изменения данных.

### `internal/service/tui`

Этот пакет содержит Bubble Tea model и view-логику.

Модель намеренно узкая:

- не читает `/proc` напрямую;
- получает список процессов через `serviceAPI`;
- получает подробности по PID через `parserAPI`;
- хранит только состояние UI, обработку клавиш, layout и rendering.

Двухпанельный интерфейс реализован через:

- `table.Model` слева;
- `viewport.Model` справа;
- стили Lip Gloss для фокуса и рамок.

Ключевые решения:

- `tick()` возвращает `nil`, если автообновление выключено;
- `dataMsg` несёт и строки, и флаг `changed`;
- таблица обновляется только при `changed=true`;
- тяжёлые детали процесса загружаются только по запросу.

### `internal/daemon`

Демон — это polling loop с hot reload конфигурации.

Его обязанности:

- периодически читать shared process snapshot;
- считать, сколько раз подряд PID нарушал лимиты;
- игнорировать защищённые процессы из whitelist;
- не пытаться повторно jail-ить процессы, уже находящиеся в jail;
- переносить целое дерево процесса в `processJail` после достижения порога нарушений;
- освобождать jailed-процессы при остановке;
- перечитывать daemon config по вычисленному Linux-пути без рестарта приложения.

Демон не знает, как устроен backend `systemd`/`cgroup`. Это делегировано в `pkg/cgroups`.

### `pkg/cgroups`

Этот пакет прячет различия между:

- transient unit-ами `systemd`;
- прямой работой с файловой системой `cgroup v2`.

Публичные операции намеренно backend-neutral:

- создать группу;
- удалить группу;
- добавить процесс в группу;
- вернуть процесс в root group;
- установить resource rows/properties.

Если нужно менять поведение resource backend-а, точка входа именно здесь.

## Runtime Flow

### Старт

Теперь есть два startup flow.

Старт клиента:

1. `awesomerctl` вычисляет Linux-путь конфига и убеждается, что файл там существует.
2. Конфиг загружается через `internal/config`.
3. Создаётся локальный collector для snapshot-ов процессов.
4. Если доступен `/run/awesomer.sock`, строится IPC-клиент для jail-state и daemon control.
5. Стартует TUI и использует локальный process inspection плюс опциональное удалённое управление демоном.

Старт демона:

1. `awesomerd` вычисляет `/etc/awesomer/config.yaml` и убеждается, что файл существует.
2. Он загружает конфиг и валидирует root-only запуск.
3. Создаёт `info.API`, общий collector и daemon logger.
4. Поднимает IPC socket server на `/run/awesomer.sock`.
5. Крутит enforcement loop до получения сигнала остановки.

### Обновление Списка Процессов

Обычный путь refresh-а:

1. Срабатывает тик TUI.
2. TUI вызывает `service.GetProcesses()`.
3. Service вызывает `collector.Processes()`.
4. Collector либо возвращает кэш, либо вызывает `parser.AllProcesses()`.
5. Service сортирует и нормализует строки.
6. Service возвращает `rows` и `changed`.
7. TUI обновляет таблицу только если `changed=true`.

### Подробная Информация По Процессу

Компактный и расширенный режимы деталей намеренно обходят collector:

- `formatedInfo()` использует `Parser.ProcessInfo(pid)`;
- `formatedBigInfo()` использует `Parser.HardObjectParse(pid)`;
- дерево процесса строится через `Parser.ProcessTree(pid)` и `Service.GetTuiTree(...)`.

Такой разделение сохраняет collector сфокусированным на горячем recurring path и не смешивает дешёвые snapshot-ы с дорогими одноразовыми запросами деталей.

### Цикл Ограничения В Демоне

Цикл демона выглядит так:

1. прочитать текущий snapshot daemon-конфига;
2. остановиться, если `run=false`;
3. взять shared process snapshot из collector-а;
4. пропустить низкие PID и имена из whitelist;
5. пропустить процессы, уже находящиеся в jail;
6. увеличить счётчик нарушений, если CPU или RAM превышают лимиты;
7. после повторяющихся нарушений получить дерево процесса и переместить всё дерево в `processJail`;
8. убрать счётчики для PID, которые уже не активны.

Путь остановки:

- вернуть все известные jailed PID в root group;
- удалить resource group или transient unit;
- вернуть первую ошибку cleanup, если она была.

## Shared State И Конкурентность

Есть три важных объекта разделяемого состояния:

### `collector.Collector`

- защищён внутренним mutex;
- разделяется демоном и сервисом;
- владеет кэшированными snapshot-ами и деревьями.

### `daemon.info.API`

- защищён собственным mutex;
- хранит, какие PID сейчас находятся в jail;
- разделяется демоном и сервисом, чтобы marker в таблице и jail-операции были согласованы.

### `service.Service`

- защищён внутренним `RWMutex`;
- хранит текущий режим сортировки;
- хранит предыдущее нормализованное состояние строк и предыдущие отрендеренные rows.

Кодовая база не пытается строить полноценную реактивную event bus архитектуру. Используется polling плюс краткоживущие shared snapshot-ы, потому что для Linux process monitoring это проще и предсказуемее.

## Обработка Ошибок

В проекте соблюдаются несколько правил:

- ошибки старта поднимаются вверх до `runApp()` и обрабатываются на верхнем уровне;
- recoverable ошибки в polling loop логируются, но не останавливают работу;
- ошибки пользовательских действий обычно логируются, а TUI продолжает работать;
- cleanup пытается сделать максимум полезной работы даже при частичных ошибках.

Практически это означает:

- ошибка чтения информации о процессе не должна ронять UI;
- shutdown демона должен пытаться выпустить все jailed PID даже если одна операция завершилась ошибкой.

## Стратегия Тестирования

Проект в основном использует package-level unit tests с инъекцией зависимостей.

Типичные паттерны:

- function variables для side effects;
- маленькие интерфейсы для parser/service/program зависимостей;
- stub-реализации вместо тяжёлых mocks;
- прямое тестирование update path у Bubble Tea модели.

Сейчас лучше всего покрыты:

- загрузка конфигурации;
- lifecycle демона и hot reload;
- сортировка и mutations в сервисе;
- update path TUI;
- выбор backend-а `cgroup`/`systemd`.

При добавлении нового поведения лучше:

1. расширить существующий интерфейс или function variable seam;
2. добавить точечный unit test в соответствующий пакет;
3. держать интеграционные TUI-тесты на уровне event flow, а не snapshot-ов рендера.

## Типичные Сценарии Изменений

### Добавить Новую Опцию Конфига

1. Обновить config structs и defaults.
2. Протащить опцию в пакет, которому принадлежит поведение.
3. Обновить example config.
4. Обновить пользовательскую документацию.
5. Добавить тест парсинга и хотя бы один поведенческий тест.

### Добавить Новое TUI-Действие

1. Расширить `serviceAPI`, если действие относится к бизнес-логике.
2. Добавить обработку клавиши в `Update()`.
3. Показать результат пользователю в правой панели.
4. Добавить TUI-тест для этого event path.

### Изменить Логику Ограничения Ресурсов

1. Решить, относится ли изменение к policy демона или к mechanics backend-а.
2. Если меняется policy, править `internal/daemon`.
3. Если меняется backend implementation, править `pkg/cgroups`.
4. Сохранять backend-neutral имена функций, пока platform-specific поведение не необходимо.

### Улучшить Производительность

Начинать оптимизацию стоит в таком порядке:

1. `internal/collector`
2. `internal/service`
3. `pkg/parser`
4. `internal/service/tui`

Этот порядок важен, потому что основная recurring стоимость сейчас в polling-е процессов и подготовке строк, а не в самом rendering-коде.

## Замечания Для Разработки

- Проект ориентирован на Linux-first поведение. Cross-platform abstractions намеренно ограничены.
- Код предпочитает явные зависимости скрытым package globals, но test seams всё ещё используют function variables там, где это делает изменения меньше.
- `gopsutil` удобен, но не бесплатен. Если profiling покажет, что он доминирует по стоимости refresh-а, следующий крупный шаг оптимизации — замена части путей на прямое чтение `/proc`.
- TUI намеренно отделён от daemon policy. Так и нужно сохранять: UI должен запрашивать действия, а не реализовывать daemon-логику внутри себя.
